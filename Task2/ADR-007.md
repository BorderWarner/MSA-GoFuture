# ADR-007. Инструменты мониторинга на C2

## Контекст

Prometheus, Grafana, Loki и Alertmanager уже присутствуют в кейсе, но потоковые задержки и трассировка не раскрыты.

## Требования

Выбрать инструменты для метрик, логов, трасс и оповещений. Показать их на C2 событийной платформы, объяснить назначение и взаимодействие с существующей инфраструктурой.

Схема сохраняет Prometheus, Grafana, Loki и Alertmanager из доменной архитектуры. Добавлены Collector, Tempo и Kafka Exporter; расширены существующие exporters; DataLens продолжает читать разрешённые витрины ClickHouse.

| Инструмент | Роль и связь |
|---|---|
| Prometheus | Pull `/metrics` сервисов, exporters, Flink, Apicurio, Collector и Alertmanager; self-metrics, вычисление SLI и alert rules |
| Kafka Exporter | Через Kafka Admin/Consumer APIs читает подтверждённые смещения групп и конечные смещения партиций; публикует lag в записях для Prometheus |
| JMX / PostgreSQL / RabbitMQ / node / kube-state exporters | JMX brokers/controllers и Debezium/Kafka Connect, статистика WAL/slot, БД и инфраструктуры; не самостоятельная система алертинга |
| OpenTelemetry Collector | Приём OTLP трасс и логов, фильтрация чувствительных полей, batching и bounded retry |
| Tempo | Хранение трасс; ссылки `trace_id` из логов и exemplars |
| Loki | Централизованные структурированные логи; ограниченные метки, поиск по `correlation_id` |
| Grafana | Запросы Prometheus/Loki/Tempo; обзоры критического пути и региональные дашборды |
| Alertmanager | Группировка, подавление зависимых алертов, доставка SRE/доменам |

Prometheus опрашивает `/metrics` сервисов, exporters и платформенных компонентов. Возраст outbox, DLQ и бизнес-инварианты публикуют обработчики; метрики Debezium доступны через JMX Exporter. Grafana запрашивает метрики, логи и трассы, Alertmanager доставляет оповещения ответственным.

Приложение отправляет логи и трассы по OTLP в Collector, который очищает и передаёт их в Loki/Tempo. Контекст `traceparent` сохраняется в заголовках HTTP и конверте Kafka; обработчик связывает consumer span с producer span, не создавая отдельную сетевую связь с Tempo.

Для Apicurio включается Prometheus endpoint на закрытом management-порту; выбранная конфигурация — `/metrics` (порт 9000), как в документации Registry. Для Collector включается endpoint собственной телеметрии. Scrape endpoints доступны только региональному Prometheus.

OpenTelemetry используется для единого контекста сигналов, но не заменяет их хранилища. Сбор и хранение региональны; недоступность центрального просмотра не останавливает локальные alert rules.

## Альтернативы

**Полностью перейти на Datadog или Elastic Observability.** Единая платформа сократила бы число интеграций, но потребовала бы заменить работающие метрики/логи, перенести правила и заново проверить размещение телеметрии. Сохранены Prometheus/Grafana/Loki/Alertmanager; добавлены только недостающие средства трассировки и сбора.

**Jaeger вместо Tempo.** Это допустимое хранилище распределённых трасс. Tempo выбран для просмотра трасс рядом с уже используемыми Grafana/Loki; необходимости вводить отдельный интерфейс расследований в кейсе нет, преимущество по скорости или стоимости без измерений не заявляется.

**Отправлять данные SDK непосредственно в Loki и Tempo.** Так пришлось бы повторять очистку чувствительных полей, маршрутизацию и retry-настройки во всех сервисах. Collector выносит эти функции в общий региональный приёмник с ограниченной очередью; exporters сохраняют pull-метрики без переноса их в отдельную новую систему.

**Оставить только `correlation_id` в логах.** Это дешевле по числу компонентов, но не показывает длительность и причинные связи producer/consumer и ветвей Saga. Логи сохранены для деталей события, Tempo — для временной картины процесса.

## Компромиссы

Tempo и Collector — два новых эксплуатационных компонента; их польза — сквозная диагностика Saga. Отказ телеметрии не блокирует бизнес-транзакцию, но вызывает отдельный алерт о потере наблюдаемости.
