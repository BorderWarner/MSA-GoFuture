# ADR-005. C2 событийной платформы

## Контекст

После выделения доменов запрос поездки затрагивает независимые Booking, Driver, Fraud и Payments. Динамическим ценам и подбору нужны свежие позиции; деньги и назначение водителя требуют согласованных переходов при частичных сбоях.

Координаты приходят с повторами, задержкой и неверным временем устройства. Региональная обработка ограничивает задержки и передачу данных; Kafka должна распределять нагрузку по агрегатам внутри региона. Сбой возможен после commit или внешней операции, но до подтверждения.

## Требования

Доработать C2 доменной архитектуры: определить события, региональные топики Kafka и партиционирование, потоковых потребителей, вид Saga и события её переходов, гарантии доставки.

### Обоснование новых элементов

Schema Registry (Apicurio) хранит версии JSON Schema и правила совместимости для независимо выпускаемых producer/consumer; без него проверка примеров в одном репозитории не фиксирует общий действующий контракт. Выбран отдельный реестр, поскольку схемы нужны и CI, и работающим обработчикам.

Региональное Object Storage для raw/checkpoints сохраняет состояние Flink при потере процесса/узла и позволяет повторить расчёт из исходных событий. Raw и checkpoints — разные buckets/префиксы с отдельными правами и retention внутри одного логического хранилища. Локальный диск worker не подходит как единственная копия восстановления.

Collector и Tempo закрывают отсутствовавший путь сквозных трасс, а расширение exporters делает видимыми Kafka и runtime. Их выбор и отклонённые инструменты описаны в [ADR-007](ADR-007.md).

### Модель доменных событий

Конверт события: `event_id` (UUID), `event_type`, `schema_version`, `occurred_at`, `ingested_at`, `tenant_id`, `region_id`, `aggregate_type`, `aggregate_id`, `aggregate_version`, `correlation_id`, `causation_id`, `traceparent`, `payload`. Время UTC. `region_id` — регион происхождения, при репликации не переписывается. Отдельный `routing_epoch` в команде определяет текущего владельца записи. Идентификаторы пользователей псевдонимные, координаты считаются чувствительными; PAN, CVV, токены входа и полные профили в события не попадают.

| События | Производитель | Потребители | Ключ порядка / минимальные данные |
|---|---|---|---|
| BookingCreated, BookingCancelled | Booking | Saga, Fraud, Analytics | tenant:booking; `quote_id`, `zone_id`, статус |
| DriverLocationUpdated | Driver ingress | Geography, Flink, Analytics | tenant:driver; координаты, `observed_at`, `device_session`, `sequence` |
| DriverReserved, DriverReservationRejected, DriverReleased | Driver | Booking, Geography, Flink | tenant:driver; `booking_id`, `reservation_id`, expiry |
| DriverAssignmentConfirmed, DriverAssignmentRejected | Driver | Booking | tenant:driver; `booking_id`, `reservation_id`, подтверждённая версия назначения |
| DriverAvailabilityChanged | Driver | Geography, Flink | tenant:driver; доступность, зона |
| FraudApproved, FraudRejected | Fraud | Booking, Payments, Analytics | tenant:booking; `decision_id`, `reason_code`, validity |
| FraudCaseResolved | Fraud | Analytics / ML | tenant:case; `booking_id`, подтверждённый исход расследования, `label_available_at` |
| PaymentAuthorized, PaymentAuthorizationFailed, AuthorizationVoided, AuthorizationVoidFailed | Payments | Booking, Analytics | tenant:payment; `booking_id`, `operation_id`, `operation_type`, `amount_minor`, currency, PSP reference; для отказа — `reason_code` |
| TripAssigned, TripStarted, TripCompleted | Booking | Driver, Payments, Notification, Analytics | tenant:booking; `driver_id`, `quote_id`, версия итоговой стоимости |
| PaymentCaptured, PaymentCaptureFailed, PaymentRefunded, PaymentRefundFailed | Payments | Booking, Notification, Analytics | tenant:payment; `operation_id`, `booking_id`, `amount_minor`, currency; для возврата — `refund_id` и исходный capture; для отказа — `reason_code` |
| PayoutCompleted, PayoutFailed | Payments/Payouts | Notification, Analytics | tenant:payout; ledger reference, результат банка |
| PriceUpdated | Pricing | Booking, Analytics | tenant:zone; версия, коэффициент, `expires_at` |
| ZoneSupplyDemandUpdated | Flink / Analytics | Pricing, Geography | tenant:zone; число запросов/доступных водителей, `window_end`, `revision` |
| RiskFeaturesUpdated | Flink / Analytics | Fraud | tenant:subject; версия признаков и `event_time` |
| GeographyZoneChanged | Geography | Pricing, Analytics | tenant:zone; версия геометрии, `effective_at` |
| NotificationDelivered, NotificationFailed | Notification | Analytics, поддержка | tenant:delivery; `event_id` исходного факта, канал, исход |

Схемы JSON Schema хранятся в Schema Registry (Apicurio); CI проверяет обратную совместимость и примеры старых потребителей. Необязательные поля добавляются совместимо. Удаление/смена смысла требует `v2` и отдельного периода перехода. Потребитель не выводит порядок из часов: проверяет версию агрегата и держит разрыв на повторную доставку/сверку с владельцем.

### Региональные топики и ёмкость Kafka

В каждом регионе независимый Kafka-кластер, не растянутый через WAN. Имя топика: `gf.<region>.<tenant>.<domain>.<stream>.v1`; tenant включён в имя для ACL изоляции партнёров. Партиционирование внутри топика — hash идентификатора агрегата. Регион отделяет место обработки; `tenant:aggregate_id` обеспечивает локальный порядок. Ключ зоны применяется только после Flink repartition. Для крупных партнёров выделяется отдельный Kafka-кластер; малые делят брокеры с квотами и отдельными топиками.

| Stream | Пример domain | Ключ | Начальное число партиций на tenant | Retention |
|---|---|---|---|---|
| events | booking, driver, payments, fraud, pricing, geography, notification | tenant:`aggregate_id` | 12; крупным 48–96 | 7 дней; платежный ledger хранится отдельно |
| location | driver | tenant:`driver_id` | 12; крупным до 256 | 6 часов |
| commands | booking, driver, payments, fraud | tenant:`target_aggregate_id` | 12; крупным 48 | 24 часа, устаревшая команда отклоняется по `deadline` |
| signals | analytics | tenant:`zone_id` либо `subject_id` | 12; крупным 48 | 24 часа; latest-проекция отдельно |
| retry / dlq | соответствующий domain | исходный ключ | 3 / 3 | 24 часа / 7 дней с ограниченным доступом |

Количество партиций назначается при подключении партнёра по измеренному профилю; приведённые размеры — классы обслуживания, не 256 партиций каждому tenant. Суммарный бюджет location-партиций нагруженного регионального кластера — не менее 256, распределённых по tenant. Изменение числа партиций меняет размещение ключей: выполнять через новый топик и контрольную границу, а не рассчитывать на сохранение порядка при горячем расширении.

Отдельные группы потребителей: `booking-saga`, `driver-commands`, `payments-commands`, `fraud-checks`, `geography-projection`, `pricing-signals`, `notification-delivery`, `flink-supply`, `flink-risk`, `analytics-ingest`; имена дополняются region/tenant. Инстансы одной группы делят партиции, разные группы получают независимые копии событий. DriverReservation может ключеваться водителем, хотя Saga ключуется поездкой: Booking коррелирует ответ по `booking_id` и проверяет ожидаемую версию Saga.

Расчётная нагрузка (предполагаемая):

- 600 тыс. поездок, 1 млн активных/доступных водителей, позиция раз в 2 с: 500 тыс. location events/s глобально. Размер с конвертом 512 байт, средняя поездка 1200 с.
- 600000 / 1200 = 500 новых поездок/с; 20 бизнес-событий на поездку ≈10 тыс./с. Умножение на коэффициент пика 2: 1 млн location и 20 тыс. business events/s.
- При равном распределении по четырём регионам: 250 тыс. location/s, 128 MB/s на регион до репликации. При приёме нагрузки соседнего региона: 500 тыс./с и 256 MB/s.
- Допущение для sizing: 3000 events/s на партицию с данным payload. 256 партиций дают 768 тыс./с; проверка должна включать перекос tenant и ключей. Пропускную способность необходимо подтвердить бенчмарком.
- RF=3: 6 часов location при пике — 8,29 TB на регион; при удвоении — 16,59 TB. С запасом 30% требуется 21,57 TB полезного дискового объёма под этот поток. Остальные топики, WAL, индексы и свободное место добавляются отдельно; экономию от сжатия не закладывать до замера.

Стартовая топология: три KRaft-контроллера по зонам и минимум шесть brokers в трёх зонах. Размер/число brokers определяются измеренной суммарной сетью, диском и CPU, а не только числом партиций. RF=3, `min.insync.replicas=2`, `acks=all`, idempotent producer, запрет unclean leader election. Ограничение квот и автомасштабирование потребителей по lag не заменяют масштабирование broker storage. При недоступности quorum запись отклоняется, а не подтверждается без сохранения.

### Потоковая обработка

Flink с PyFlink обрабатывает три независимых job; Analytics/Data владеют инфраструктурой, продуктовые команды — правилами результата.

| Job | Вход и состояние | Выход и использование |
|---|---|---|
| SupplyDemand | BookingCreated/Cancelled, TripAssigned, DriverLocationUpdated/AvailabilityChanged; latest-позиция по driver, активные незакрытые заказы по booking | После repartition по tenant:zone — ZoneSupplyDemandUpdated; Pricing обновляет коэффициенты, Geography ранжирует зоны |
| RiskFeatures | События поездок и платежей, допустимые агрегаты перемещений; окна 1 и 15 минут | RiskFeaturesUpdated → Fraud; решение Fraud отдельно сохраняется владельцем |
| AnalyticsIngest | События всех восьми доменов; проверка схемы и `event_id` | Региональные raw-данные и ClickHouse; дедупликация и проверка контрактов |

SupplyDemand обновляет результат каждую секунду по текущему состоянию и окнам 10/60 с. Используется event time, watermark с допуском 2 с, idle source после 3 с. События до 30 с опоздания корректируют результат с новой `revision`; более старые идут в поток поздних данных для аналитики. Время устройства отличается от серверного более чем на 30 с — quarantine; последнее положение не откатывается назад. Принимается только возрастающий `(device_session, sequence)`, новая session валидируется Driver.

Позиция старше 5 с исключает водителя из немедленных кандидатов. Geography предлагает контролируемое ожидание до 30 с и учитывает дефицит соседних зон; Driver всё равно подтверждает резерв. Pricing выдаёт quote с TTL 60 с; при отсутствии свежего сигнала 10 с использует последний безопасный коэффициент, через 60 с — базовый тариф с явным флагом деградации. Старый quote остаётся обязательством до TTL.

Checkpoint каждые 2 с в региональное объектное хранилище, timeout 30 с, внешние checkpoints сохраняются; savepoint перед изменением state schema. Источник Kafka восстанавливает смещения из checkpoint. Выход Kafka — транзакционный sink с уникальным transactional ID prefix, `read_committed`, transaction timeout 5 мин, предельный restart 2 мин. Видимость результата задерживается до checkpoint, поэтому это включено в бюджет свежести 5 с. В Redis/ClickHouse применяются versioned upsert и дедупликация; транзакции Kafka не дают общей транзакции с ними.

### Saga поездки

Выбрана **Parallel Saga: асинхронная коммуникация, итоговая согласованность, оркестрация**.

| Измерение | Реализация в GoFuture | Причина выбора |
|---|---|---|
| Асинхронная коммуникация | Booking отправляет команды через outbox/CDC/Kafka и получает факты; таймеры не удерживают HTTP-запрос | Шаги и внешний PSP могут отвечать с задержкой, потребители масштабируются независимо |
| Итоговая согласованность | Каждый домен фиксирует локальную транзакцию; промежуточные состояния видимы, отказ запускает компенсации | Нельзя включить все БД и PSP в одну транзакцию; завершение поездки и успешное списание — разные факты |
| Оркестрация | Booking хранит ход процесса, deadlines и ожидаемые ответы | Один владелец отвечает за отмену, зависший резерв, неопределённый платёж и восстановление после сбоя |

Зависимые шаги выполняются последовательно: Fraud → авторизация → резерв водителя → подтверждение назначения. Независимые компенсации ReleaseDriver и VoidAuthorization могут выполняться одновременно. Синхронные чтения quote/кандидатов и HTTP Payments → PSP не меняют асинхронный протокол координации между участниками Saga.

Оркестратор — внутренний модуль Booking, выбранный в [ADR-002](../Task1/ADR-002.md). Состояние Saga, inbox, абсолютный `deadline` таймера и следующий outbox сохраняются одной транзакцией. Worker получает ограниченную lease; переход выполняется с проверкой версии Saga. После перезапуска продолжается сохранённый шаг с прежними идентификаторами и сроками.

#### Реестр операций

**Компенсируемая** операция допускает нейтрализацию результата до pivot. **Необратимая** пересекает границу, после которой требуется отдельное урегулирование. **Повторяемая** доводится до подтверждённого результата либо окончательного бизнес-отказа. Для всех типов обязательна идемпотентность; технические повторы ограничены сроком операции.

| Операция | Владелец и результат | Тип | Компенсация / ограничение |
|---|---|---|---|
| CreateBooking | Booking: принять quote, создать поездку и Saga, сохранить BookingCreated и CheckFraud в outbox | Компенсируемая | CancelBooking; история сохраняется |
| CheckFraud | Fraud: сохранить решение и опубликовать FraudApproved либо FraudRejected | Повторяемая | Нет; отказ или истечение 2 с закрывает ожидание без авторизации платежа |
| AuthorizePayment | Payments: подтвердить удержание суммы у PSP, сохранить PaymentAuthorized | Компенсируемая | VoidAuthorization; неизвестный исход сначала сверяется |
| ReserveDriver | Driver: атомарно создать резерв с `reservation_id` и TTL, опубликовать DriverReserved | Компенсируемая | ReleaseDriver для того же `reservation_id` |
| ConfirmAssignment | Driver: перевести действующий резерв в назначение, сохранить DriverAssignmentConfirmed | Компенсируемая до TripStarted | ReleaseDriver; после начала поездки освобождение происходит при её завершении |
| StartTrip | Booking: принять начало назначенной поездки, записать `IN_PROGRESS` и TripStarted | Необратимая, pivot | Обычной компенсации нет; прерывание оформляется по правилам фактически оказанной услуги |
| CompleteTrip | Booking: зафиксировать фактический исход, итоговую сумму и TripCompleted | Повторяемая после pivot | Нет; завершённая поездка не отменяется из-за ошибки оплаты |
| CapturePayment | Payments: списать согласованную итоговую сумму в рамках авторизации, сохранить PaymentCaptured | Повторяемая после pivot | Подтверждённое списание возвращается только отдельной операцией RefundPayment |
| ReleaseDriver | Driver: закрыть конкретный резерв/назначение, сохранить DriverReleased | Повторяемая | Используется и при компенсации, и после TripCompleted; не затрагивает другое назначение |
| VoidAuthorization | Payments: подтвердить снятие удержания, сохранить AuthorizationVoided | Повторяемая | Не заменяет возврат уже списанных средств |
| CancelBooking | Booking: после завершения компенсаций записать `CANCELLED` и BookingCancelled | Повторяемая | Не удаляет заказ, журнал шагов и финансовые ссылки |
| Сверка операции | Payments: выяснить результат PSP по прежнему `operation_id`, сохранить подтверждённый факт | Повторяемая | Локальная задача Payments; отсутствие ответа не считается отсутствием эффекта |
| RefundPayment | Payments: зарегистрировать `refund_id` и выполнить отдельный возврат по исходному capture | Необратимая в процессе возврата | Автоматического обратного списания нет; повторы возвращают результат того же `refund_id` |
| Доставка уведомления | Notification: обработать факт с устойчивым delivery key, сохранить результат доставки | Повторяемая | Ошибка уведомления не запускает денежную операцию и не меняет статус поездки |

CreateBooking, StartTrip, CompleteTrip и CancelBooking обозначают операции владельца Booking. Межсервисные CheckFraud, AuthorizePayment, ReserveDriver, ConfirmAssignment, ReleaseDriver, VoidAuthorization, CapturePayment и RefundPayment — команды в существующих Kafka command topics. Факты об их результате публикуются в event topics; сверка PSP выполняется внутри Payments.

#### Граница компенсации и состояния

**Pivot — подтверждённое начало поездки TripStarted.** Booking принимает StartTrip только для `ASSIGNED` с актуальным назначением и без принятой отмены. Приложение водителя начинает поездку после подтверждения Booking; локальная отметка устройства не является фактом начала. До pivot отказ запускает освобождение резерва/назначения и снятие авторизации. После pivot прерывание требует фиксации фактически оказанной услуги и расчёта по бизнес-правилам через CompleteTrip, а не перехода к `CANCELLED`. Watchdog 4 ч вызывает разбор поддержки; он не завершает поездку и не списывает деньги автоматически.

Разделяются три состояния: `saga_state` — ход координации в Booking; `trip_status` — `CREATED`, `ASSIGNED`, `IN_PROGRESS`, `COMPLETED` или `CANCELLED`; `payment_status` — подтверждённый финансовый результат в Payments. Booking хранит его версионированную проекцию из событий. Например, поездка уже `COMPLETED`, пока Saga находится в `SETTLING`, а результат capture выясняется. Возврат хранит собственный `refund_status`.

#### Переходы основной Saga

В первых двух столбцах указано `saga_state`. Действия строки, новые таймеры и команды outbox фиксируются вместе с переходом. Ответ принимается только для ожидаемой операции, `reservation_id` и версии процесса.

| Исходное состояние | Следующее состояние | Команда / событие | Условия, действия и срок |
|---|---|---|---|
| Saga отсутствует | `FRAUD_PENDING` | CreateBooking → BookingCreated; CheckFraud | Quote принят в пределах TTL 60 с; `trip_status`=`CREATED`; ожидание Fraud ≤2 с |
| `FRAUD_PENDING` | `AUTH_PENDING` | FraudApproved → AuthorizePayment | Решение действительно для этой поездки; результат авторизации ожидается 5 с |
| `FRAUD_PENDING` | `CANCELLING` | FraudRejected, тайм-аут или отмена | Закрыть ожидание; поздний FraudApproved не запускает авторизацию |
| `AUTH_PENDING` | `DRIVER_PENDING` | PaymentAuthorized → ReserveDriver | Отмена ещё не принята; сохранить payment reference; общее окно подбора 30 с |
| `AUTH_PENDING` | `AUTH_PENDING` | Нет достоверного результата за 5 с | Payments сверяет `operation_id`; при необходимости `payment_status`=`RESOLUTION_PENDING`; резерв не создаётся |
| `AUTH_PENDING` | `CANCELLING` | PaymentAuthorizationFailed или отмена | Отказ должен быть окончательным; при неизвестном исходе сохранить требование снять возможную авторизацию |
| `DRIVER_PENDING` | `ASSIGNMENT_PENDING` | DriverReserved → ConfirmAssignment | Проверить `reservation_id` и оставшийся TTL 45 с; подтверждение ожидается ≤5 с и до expiry |
| `DRIVER_PENDING` | `DRIVER_PENDING` | DriverReservationRejected | Отказ подтверждён, резерва нет; следующий кандидат получает новый `reservation_id` в оставшемся окне 30 с |
| `DRIVER_PENDING` | `DRIVER_RELEASING` | Нет ответа ReserveDriver за 2 с | Отправить ReleaseDriver прежнему кандидату; новый резерв до подтверждения освобождения не создавать |
| `DRIVER_RELEASING` | `DRIVER_PENDING` / `CANCELLING` | DriverReleased | При оставшемся окне — следующий кандидат; иначе отмена. Неизвестный результат не продлевает окно подбора |
| `DRIVER_PENDING` / `DRIVER_RELEASING` | `CANCELLING` | Исчерпаны 30 с либо принята отмена | Закрыть подбор, сохранить все незавершённые попытки для компенсации |
| `ASSIGNMENT_PENDING` | `ASSIGNED` | DriverAssignmentConfirmed → TripAssigned | Только текущая попытка и отсутствие отмены; `trip_status`=`ASSIGNED` |
| `ASSIGNMENT_PENDING` | `CANCELLING` | DriverAssignmentRejected, тайм-аут, истечение резерва или отмена | ReleaseDriver и VoidAuthorization; позднее подтверждение не назначает поездку повторно |
| `ASSIGNED` | `IN_PROGRESS` | StartTrip → TripStarted | Атомарно проверить версию и отсутствие отмены; `trip_status`=`IN_PROGRESS`, pivot пройден |
| `ASSIGNED` | `CANCELLING` | Принята отмена до StartTrip | Начало поездки после этого перехода запрещено; запустить компенсации |
| `IN_PROGRESS` | `SETTLING` | CompleteTrip → TripCompleted | `trip_status`=`COMPLETED`; сохранить согласованную сумму, отправить CapturePayment и ReleaseDriver независимо |
| `SETTLING` | `SETTLING` | Получен только один результат либо capture неизвестен | Сохранить факт; не удерживать водителя из-за оплаты. После 10 с без исхода capture — сверка Payments |
| `SETTLING` | `SUCCEEDED` | PaymentCaptured и DriverReleased | Оба результата подтверждены; `trip_status` остаётся `COMPLETED` |
| `SETTLING` | `PAYMENT_DUE` | PaymentCaptureFailed и DriverReleased | Окончательный отказ capture: сохранить задолженность и завершить исходную Saga с этим результатом; дальнейшее взыскание — отдельная операция Payments |
| `CANCELLING` | `COMPENSATING` | Сохранён план необходимых компенсаций | ReleaseDriver и VoidAuthorization можно отправить одновременно; неизвестный результат включён в план, а не пропущен |
| `COMPENSATING` | `CANCELLED` | Все требуемые результаты подтверждены → BookingCancelled | Нет открытого резерва/назначения, авторизация снята либо достоверно не возникла; `trip_status`=`CANCELLED` |

`SUCCEEDED`, `PAYMENT_DUE` и `CANCELLED` — терминальные результаты исходной Saga. Если эффектов ещё не было, `CANCELLING` → `COMPENSATING` → `CANCELLED` можно выполнить одной локальной транзакцией. При незавершённом освобождении после TripCompleted процесс остаётся `SETTLING`; подтверждённая оплата не скрывает занятость водителя. Возраст компенсации/освобождения или выяснения денежного результата >60 с вызывает алерт и разбор; это не переход к успеху по таймеру.

#### Состояния оплаты

Таблица описывает `payment_status` в Payments. Для каждой авторизации, capture и void сохраняются тип, неизменный `operation_id`, сумма, валюта и результат PSP. В `RESOLUTION_PENDING` дополнительно сохраняется исходное состояние и намерение `cancel_requested`. Пока исход операции не установлен, конфликтующая денежная операция не отправляется. Допуск вызова PSP фиксируется до отправки и сериализуется с отменой по версии операции: отсутствие допуска позволяет отменить вызов, наличие допуска требует сверки даже после падения worker.

| Исходное состояние | Следующее состояние | Основание | Действие / ограничение |
|---|---|---|---|
| Платёж отсутствует | `AUTH_PENDING` | AuthorizePayment | Сохранить intent и `operation_id` до обращения к PSP |
| Платёж отсутствует / `AUTH_PENDING` | `VOIDED` | VoidAuthorization принят до допуска вызова авторизации | Сохранить запрет этой авторизации и AuthorizationVoided с признаком отсутствия удержания; поздний AuthorizePayment не обращается к PSP |
| `AUTH_PENDING` | `RESOLUTION_PENDING` | VoidAuthorization принят после допуска вызова авторизации | Сохранить `cancel_requested`; выяснить результат и снять удержание, если оно возникло |
| `AUTH_PENDING` | `AUTHORIZED` | Авторизация подтверждена → PaymentAuthorized | Сохранить reference и срок действия; при `cancel_requested` сразу продолжить void, не подбор водителя |
| `AUTH_PENDING` | `AUTH_FAILED` | Подтверждён окончательный отказ → PaymentAuthorizationFailed | Денежного удержания нет; компенсация авторизации не нужна |
| `AUTHORIZED` | `VOID_PENDING` | VoidAuthorization | Сначала сохранить намерение снять удержание; capture для отменённой поездки запрещён |
| `VOID_PENDING` | `VOIDED` | Снятие удержания подтверждено → AuthorizationVoided | Истечение авторизации допустимо как результат только после подтверждения PSP |
| `VOID_PENDING` | `VOID_PENDING` | Подтверждён отказ void → AuthorizationVoidFailed | Удержание не объявляется снятым; разбор Payments и повтор только при допустимости по причине отказа |
| `AUTHORIZED` | `CAPTURE_PENDING` | CapturePayment после TripCompleted | Проверить сумму/валюту и доступную авторизацию; нарушение условий даёт окончательный отказ без вызова PSP |
| `AUTHORIZED` | `CAPTURE_FAILED` | Условия capture не выполнены → PaymentCaptureFailed | Не вызывать PSP; сохранить причину задолженности и задачу снятия остаточного удержания |
| `CAPTURE_PENDING` | `CAPTURED` | Списание подтверждено → PaymentCaptured | Ledger фиксирует единственный эффект; исходная Saga ждёт также DriverReleased |
| `CAPTURE_PENDING` | `CAPTURE_FAILED` | Окончательный отказ → PaymentCaptureFailed | Подтверждённого списания нет; учесть задолженность. Остаточное удержание снять/сверить в отдельной задаче Payments |
| `AUTH_PENDING` / `VOID_PENDING` / `CAPTURE_PENDING` | `RESOLUTION_PENDING` | Запрос отправлен, результат неизвестен | Сверка по тому же `operation_id`; тайм-аут не является подтверждённым отказом |
| `RESOLUTION_PENDING` | `AUTHORIZED` / `VOIDED` / `CAPTURED` | Сверка подтвердила соответствующий эффект | Сохранить результат и факт; при отмене поздняя авторизация ведёт к void |
| `RESOLUTION_PENDING` | `AUTH_PENDING` / `VOID_PENDING` / `CAPTURE_PENDING` | PSP достоверно подтвердил отсутствие эффекта | Допустим повтор той же операции с прежним ключом. При отменённой авторизации вместо повтора зафиксировать `AUTH_FAILED` с причиной отмены |
| `RESOLUTION_PENDING` | `AUTH_FAILED` / `VOID_PENDING` / `CAPTURE_FAILED` | Сверка подтвердила окончательный отказ соответствующей операции | Для void удержание остаётся незакрытым; для capture поездка остаётся `COMPLETED` |

Новый `operation_id` не используется для обхода неизвестного исхода или окончательного бизнес-отказа. Если PSP не даёт надёжного подтверждения отсутствия эффекта, сохраняется `RESOLUTION_PENDING` и требуется разбор Payments. Повторный ответ с тем же результатом не создаёт новую проводку. Payouts начинает отдельную идемпотентную операцию только по подтверждённым проводкам ledger с учётом возвратов.

#### Ошибки, повторы и конкуренция

Команда содержит `command_id`, `saga_id`, ожидаемую версию шага, `deadline` и `routing_epoch`. Повтор доставки сохраняет `command_id`; отдельный шаг получает новый `command_id`, но повтор той же денежной операции сохраняет `operation_id`. Inbox команд имеет уникальный `(tenant_id, command_id)`, inbox фактов — `(tenant_id, event_id)`. Booking назначает `reservation_id` до отправки ReserveDriver; он не меняется при повторе этой попытки.

| Ситуация | Состояние / результат | Обработка | Условие продолжения |
|---|---|---|---|
| Дубль команды или факта | Состояние не меняется повторно | Inbox и ключ операции возвращают сохранённый результат; обработчик не повторяет внешний эффект | Допускается повторная доставка прежнего факта |
| Техническая ошибка до эффекта | Текущий шаг остаётся ожидающим | Backoff 1/5/30 с с jitter, только в пределах `deadline`; для коротких шагов оставшийся срок ограничивает число попыток | Окончательный бизнес-отказ не повторяется как transient |
| Ответ Fraud конкурирует с таймером | `AUTH_PENDING` либо `CANCELLING` | Проверка версии и состояния ожидания допускает ровно один исход; после `deadline` разрешение не принимается | Просрочка не превращается в FraudApproved |
| StartTrip конкурирует с отменой | `IN_PROGRESS` либо `CANCELLING` | Обе операции меняют одну версию Booking: победившая транзакция закрывает другую ветвь | После `IN_PROGRESS` обычная отмена запрещена; после `CANCELLING` StartTrip отклоняется |
| ReserveDriver/ConfirmAssignment пришли после ReleaseDriver | Резерв остаётся закрытым | Driver сохраняет признак закрытия `reservation_id` даже при ещё не полученном ReserveDriver; поздние команды не создают и не восстанавливают назначение | DriverReleased подтверждает закрытие попытки, а не только отсутствие строки на момент чтения |
| Поздний DriverReserved/DriverAssignmentConfirmed | `DRIVER_RELEASING` либо `COMPENSATING` | Коррелировать прежний `reservation_id`, выполнить/подтвердить ReleaseDriver; не публиковать TripAssigned для закрытой попытки | Новый кандидат — только после подтверждённого закрытия прежнего |
| Истёк TTL резерва | Назначение не предполагается автоматически снятым | Driver подтверждает закрытие резервирования; подтверждённое назначение сохраняется до ReleaseDriver/завершения | TTL исходного резерва не освобождает уже назначенного водителя |
| Авторизация пришла после принятой отмены | `COMPENSATING` | Payments сохраняет реальный результат; выполняется VoidAuthorization с устойчивым ключом | `CANCELLED` только после AuthorizationVoided либо доказанного отсутствия авторизации |
| VoidAuthorization доставлен раньше AuthorizePayment | Авторизация не возникает позднее | Payments сохраняет `cancel_requested` для исходного `operation_id`, даже если intent авторизации ещё не получен | Поздняя команда возвращает сохранённый исход отмены без обращения к PSP и без изменения `VOIDED` |
| Компенсация завершилась частично или отказала | `COMPENSATING` | Каждая ветвь хранит собственный исход; завершённая не запускается заново. После 60 с — алерт и ответственный | Закрытие Saga требует всех результатов; DLQ не считается компенсацией |
| Booking упал после commit / до подтверждения Kafka | Сохранённый шаг восстанавливается | Новый worker использует lease и версию; outbox доставляет прежние команды, inbox подавляет дубли, `deadline` не начинается заново | Старый worker не может записать переход с устаревшей версией |
| Ответ PSP или callback потерян | `RESOLUTION_PENDING` | Сверить тип/ключ/сумму операции; ответ и callback применяются идемпотентно | До достоверного исхода запрещена новая конфликтующая операция |
| Денежный/Driver ответ пришёл после терминального результата | Исходная Saga не открывается заново | Старый факт известной версии — дубль. Противоречащий сохранённому исходу новый эффект — инцидент и сверка владельца, не молчаливое игнорирование | Урегулирование связано с исходной операцией и отражается в учёте |
| Notification не доставил сообщение | Финансовый результат и `trip_status` прежние | Повторить только доставку по delivery key | Ошибка уведомления не повторяет capture, void или refund |

Driver атомарно проверяет `reservation_id`, `booking_id`, expiry, версию назначения и `routing_epoch` перед ConfirmAssignment. ReleaseDriver содержит ожидаемое назначение и закрывает только его; поздняя компенсация не освобождает водителя от следующей поездки. Записи закрытых попыток и отменённых денежных intent хранятся не меньше допустимого окна replay. Устаревшие команды отвергаются по `deadline`; повтор уборки незавершённого эффекта оформляется явно с тем же ключом эффекта и новым разрешённым сроком.

#### Отдельный возврат после списания

RefundPayment запускает процесс в Payments, связанный с исходными `payment_id`, capture `operation_id` и `booking_id`. Основание и полномочия проверяются до вызова PSP. Возврат не является компенсацией оказанной поездки: `trip_status`=`COMPLETED`, исходный capture остаётся `CAPTURED`, а ledger отдельно хранит возврат и итоговую возвращённую сумму. Исходная Saga не переоткрывается. Возврат при уже выполненной выплате требует отдельной сверки обязательств; технический retry не обращает выплату вспять.

| Исходное состояние возврата | Следующее состояние | Событие / условие | Действие |
|---|---|---|---|
| Возврат отсутствует | `REFUND_REQUESTED` | RefundPayment принят с устойчивым `refund_id` | Сохранить основание, сумму, валюту, инициатора и ссылку на capture; дубль возвращает этот процесс |
| `REFUND_REQUESTED` | `REFUND_PROCESSING` | Capture подтверждён, права и сумма допустимы | Атомарно зарезервировать сумму возврата и сохранить intent до обращения к PSP |
| `REFUND_REQUESTED` | `REFUND_REJECTED` | Нет основания/прав либо превышен доступный остаток | Зафиксировать отказ без денежного вызова; исходная поездка не меняется |
| `REFUND_PROCESSING` | `REFUND_COMPLETED` | Возврат подтверждён → PaymentRefunded | Записать проводку и учесть сумму как возвращённую; уведомление обрабатывается отдельно |
| `REFUND_PROCESSING` | `REFUND_PROCESSING` | Временная ошибка до отправки запроса | Ограниченный повтор с тем же `refund_id`; спустя 60 с — алерт, а не автоматический успех |
| `REFUND_PROCESSING` | `REFUND_RESOLUTION_PENDING` | Результат отправленного запроса неизвестен | Сохранить резерв суммы и сверять тот же `refund_id`; новый возврат не дублирует эту сумму |
| `REFUND_RESOLUTION_PENDING` | `REFUND_COMPLETED` / `REFUND_PROCESSING` | Сверка подтвердила исполнение / достоверное отсутствие эффекта | Зафиксировать результат либо повторить прежнюю операцию; техническое отсутствие ответа не освобождает резерв суммы |
| `REFUND_PROCESSING` / `REFUND_RESOLUTION_PENDING` | `REFUND_REJECTED` | Подтверждён окончательный отказ без возврата → PaymentRefundFailed | Освободить зарезервированную сумму, сохранить причину для разбора; бизнес-отказ не повторяется автоматически |
| `REFUND_COMPLETED` / `REFUND_REJECTED` | То же состояние | Повтор запроса или известного результата | Вернуть сохранённый исход; противоречащий ему новый финансовый факт требует сверки |

Доступный остаток — подтверждённая сумма capture минус завершённые и зарезервированные незавершённые возвраты в той же валюте. Проверка и резерв суммы выполняются одной локальной транзакцией Payments, чтобы конкурирующие запросы не превысили остаток. Повтор `refund_id` с другой суммой отклоняется. Новый возврат после окончательного отказа допускается только как отдельно одобренный запрос после установления отсутствия эффекта прежнего.


### Надёжная доставка

Транзакционные факты: бизнес-таблица + outbox в PostgreSQL → Debezium → Kafka. Вход: inbox с уникальным `(tenant_id, event_id)` + бизнес-эффект + новый outbox в одной локальной транзакции; offset фиксируется после commit. При рестарте повтор отбрасывается inbox. Хранение inbox не короче максимального окна replay; денежные `operation_id` сохраняются весь срок хранения ledger.

Телеметрия: Driver ingress проверяет tenant/session/`sequence`, публикует позицию с `acks=all` и только затем подтверждает HTTP-запрос. PostgreSQL не принимает каждую позицию; latest-проекция восстанавливается из Kafka. Устройство держит ограниченный буфер и повторяет тот же `sequence`. При переполнении/отключении связи пропуски явно учитываются; это допустимая потеря непринятой телеметрии, не бизнес-событий.

Повторы transient-ошибок: 1, 5, 30 с с jitter и общим `deadline` команды. Для операций с порядком блокируется конкретный агрегат, последующие версии буферизуются; свободное отправление retry в хвост не считается сохранением порядка. После лимита — DLQ с причиной, исходными IDs и schema version; для Saga одновременно фиксируется состояние ошибки. Replay выполняется оператором выбранного tenant после устранения причины, с прежним `event_id` и dry-run проверки; side effects защищены бизнес-ключом. Невосстановимый объект требует сверки с владельцем.

| Отказ | Ожидаемое поведение |
|---|---|
| Commit БД прошёл, CDC остановлен | Outbox остаётся; алерт по возрасту, ограничение WAL; после восстановления публикация продолжается |
| Kafka приняла событие, ответ потерян | Idempotent producer уменьшает повторы; inbox всё равно обязателен |
| Потребитель упал после локального commit | Offset мог не сохраниться; повтор не создаёт второй эффект |
| Недоступен PSP | Ограниченные повторы, circuit breaker; неизвестный исход проверяется по прежнему `operation_id` |
| Ошибка схемы | Quarantine/DLQ с владельцем; не подтверждать успешную обработку бизнес-команды |
| Исчерпан Kafka quorum | Новые события не подтверждаются; API возвращает retryable ошибку, outbox сохраняет уже принятые транзакции |

Exactly-once ограничивается Flink state + транзакционным Kafka sink при корректных checkpoints; SQL и PSP требуют своих механизмов идемпотентности.

## Альтернативы

**Хореография вместо оркестрации.** Подходит независимым реакциям Notification/Analytics, но при отмене поездки распределяет знание о резерве, авторизации и поздних ответах между сервисами. Поэтому основной процесс координирует Booking. Синхронная цепочка увеличила бы зависимость доступности участников; общая атомарная транзакция с PSP и длительной поездкой неприменима. Выбраны асинхронные команды, локальные транзакции и явные компенсации.

**RabbitMQ Streams вместо Kafka.** Streams поддерживает повторное чтение журнала и является реальной альтернативой; существующие очереди Celery сами по себе этим журналом не становятся. Kafka выбран для общего пути Debezium → Flink и независимых групп потребителей; переход на Streams потребовал бы другого набора интеграций и отдельного подтверждения нагрузочного профиля.

**Kafka Streams или Spark Structured Streaming.** Kafka Streams потребовал бы JVM-код для основных обработчиков, а второй потоковый движок увеличил бы состав эксплуатации. Выбран уже указанный в кейсе Flink с Python API и event-time/stateful jobs; превосходство по производительности не предполагается без измерений.

**Схемы только в Git, Confluent Schema Registry, checkpoints на диске worker.** Git остаётся источником изменения схем, но не единственным каталогом версий для работающих потребителей; Apicurio выбран как отдельный реестр JSON Schema без принятия целой платформы поставщика. Confluent Schema Registry функционально допустим, но дополнительных требований в его пользу нет. Object Storage выбран для переживающих потерю worker checkpoints и raw, вместо локального диска.

**Прямая публикация после commit и бесконечный retry.** Первая оставляет окно потери факта, второй скрывает повреждённое сообщение и задерживает здоровый поток. Outbox/inbox и ограниченные retry/DLQ дают проверяемые точки восстановления; публикация всех SQL-изменений наружу отклонена, чтобы не сделать внутреннюю схему БД публичным контрактом.

## Компромиссы

Каталог требует владельца контракта и проверки совместимости. Replay не должен повторно отправлять деньги и уведомления: технический replay и восстановление бизнес-операции имеют разные полномочия.

Топики на tenant увеличивают число партиций и операционные расходы. Platform устанавливает лимит топиков/партиций на кластер и переносит крупного tenant в выделенный контур до исчерпания лимита. Гарантии описанного кластера ограничены отказами внутри региона.

Частые checkpoints требуют измерения размера состояния и нагрузки на хранилище. При невозможности удержать бюджет свежести job масштабируется или пересматривается окно; устаревший результат не выдаётся за актуальный.

Booking содержит процессную связанность. Его оркестратор горизонтально масштабируется по Saga, но владелец одной Saga единственный. При отказе Booking участники сохраняют собственные инварианты и TTL; восстановление не начинает процесс заново.

Inbox/outbox и DLQ требуют хранения и уборки по политике retention. Автоматическое удаление неопубликованного outbox запрещено. Сохранность при потере всего региона требует отдельного резервирования.
