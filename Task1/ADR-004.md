# ADR-004. План миграции данных

## Контекст

Объём данных неизвестен, в старой БД есть междоменные связи и незавершённые операции. Полное копирование с длительной остановкой записи не подходит.

## Требования

Описать перенос данных каждого домена при большом объёме: подготовку, пакетное копирование, CDC, сверку, передачу права записи и откат с минимальным простоем.

## Решение

Действующие legacy-домены записывают бизнес-факты в outbox той же транзакции; Debezium передаёт их выделенным потребителям через доменные topics. Отдельно Debezium читает snapshot/WAL старой БД в migration topics. Python-процесс переноса потребляет их, преобразует записи и выполняет versioned upsert в БД владельца до переключения записи. Для каждого домена используются отдельные учётные данные и контрольная точка переноса. Бизнес-события outbox идут в доменные топики; записи от переноса не публикуются как новые бизнес-операции. Сам Debezium не выполняет преобразование и запись целевой схемы.

Общая процедура для каждого домена и когорты tenant/region:

1. Инвентаризировать таблицы, индексы, FK, персональные данные, объём `V`, темп изменений `r`, допустимое окно и владельцев записей. Отделить архив от оперативных данных. Зафиксировать точку восстановления и проверить резервную копию.
2. Создать целевую схему, роли, новые ключи, индексы и ограничения. Перенести внешние ссылки в идентификаторы/проекции. Унаследованные числовые ключи сохранять или вести однозначную таблицу соответствия.
3. Зафиксировать согласованный snapshot и позицию WAL; обеспечить удержание WAL до завершения копирования. Копировать keyset-пакетами с checkpoint, ограничением I/O и паузой при росте p95/replication lag. Оценка времени: `V / эффективная_скорость`; догоняющая обработка должна быть быстрее `r`.
4. Применить накопленный CDC с учётом версии записи и tombstone. Повтор пакета/изменения безопасен. Контролировать свободный диск и replication slot lag; при переполнении не удалять историю молча, а прервать перенос и начать новый согласованный snapshot.
5. Сравнить количества и хеши по диапазонам ключей, выборки содержимого, агрегаты и доменные инварианты. Сделать теневое чтение; записывать расхождения в отчёт миграции без PII.
6. Остановить старые команды выбранной когорты, дождаться транзакций, догнать CDC до последнего LSN и повторить сверку. Переключить ownership epoch и маршруты, запретить монолиту изменять данные этой когорты. Повторы клиентов имеют прежний Idempotency-Key. При превышении 30 с отменить переключение до открытия записи новому сервису.
7. После переключения вести журнал изменений новой системы и обратную проекцию в старую схему только при доказанной совместимости. Мониторить 7 дней; старые данные сохранять read-only до завершения срока отката и политики хранения.

Ограничения логической репликации PostgreSQL учитываются отдельно: DDL и последовательности синхронизируются процедурой миграции, большие объекты переносятся отдельно. До открытия записей проверить следующий ID и соответствие схем.

| Домен | Данные и перенос | Специальная сверка и условие переключения |
|---|---|---|
| Notification | Устройства/согласия, шаблоны и delivery log; snapshot + CDC, затем очередь нового сервиса | Уникальность `(event_id, channel, recipient_ref)`; старые задачи дренированы, pending попытки имеют единственного исполнителя |
| Analytics | Исторические факты в ClickHouse пакетами по дню; события догоняют high-water mark | Число поездок и финансовые итоги по tenant/дню совпадают; повторный импорт дедуплицируется; старые ETL выключены после сверки |
| Geography | Зоны/правила snapshot + CDC; Elasticsearch перестраивается из принадлежащих доменам источников | Совпадение маршрутов на контрольных точках; полнота индекса, свежесть позиций. Историю координат целиком в индекс не копировать |
| Driver | Профили и резервы snapshot + CDC; позиции через поток с порядком по `driver_id` | Ни один водитель не имеет двух действующих резервов; старые активные резервы обслуживаются через фасад до истечения/завершения |
| Pricing | Тарифы и версии правил, действующие quote | Совпадение расчёта на эталонной выборке; действующие quote принимаются до TTL, повторный расчёт не меняет согласованную цену |
| Fraud | Правила, решения и разрешённые признаки; replay событий для проекций | Результаты известных кейсов и срок актуальности признаков; незавершённые проверки не теряются, недостоверные решения переводятся на безопасный путь |
| Payments/Payouts | Ledger, авторизации, capture/refund/payout и idempotency ledger; snapshot + CDC, callbacks через единый маршрутизатор | Суммы дебет=кредит в валюте, сверка с PSP/банком, статус каждой незавершённой операции. Новые списания запрещены до сверки неопределённых результатов |
| Booking | Завершённая история пакетно, новые заказы — новая когорта, активные поездки закреплены за старой | Согласованность статусов, назначений и оплаты; переносить активную Saga только отдельной процедурой после остановки её владельца, по умолчанию дождаться завершения |

До передачи записи откат состоит в отключении чтения из новой БД и продолжении старого пути. После передачи сначала новому сервису запрещается изменять данные, затем обратная проекция догоняется до контрольной позиции и сверяется; только после этого выдаётся новый epoch старому владельцу. Если обратное преобразование неполно или произошёл необратимый платёж, применяется исправление вперёд и сверка с PSP; старая резервная копия не становится источником актуального ledger. Повтор списания/выплаты использует тот же внешний ключ идемпотентности, возврат является отдельной операцией.

## Альтернативы

**Копирование через `pg_dump` с остановкой записи.** Это простой вариант для небольшой БД и заранее измеренного окна, но здесь объём неизвестен и общая пауза неприемлема. Выбран snapshot с догоняющим CDC; короткая блокировка применяется только к проверенной когорте при передаче права записи.

**Dual-write в монолит и новую БД или двунаправленная репликация.** При частичном сбое два состояния расходятся, а денежный эффект нельзя отменить повторным SQL. Поэтому в каждый момент запись бизнес-операций выполняет одна назначенная реализация; перенос работает до переключения, а обратная проекция допускается только с доказанной совместимостью.

**Оставить общую БД либо применить CDC напрямую без Python-преобразования.** Общие таблицы сохраняют связанность релизов и прав доступа; простой перенос строк не разделит междоменные ключи и инварианты. Python-процесс выполняет явное преобразование и сверку новой схемы; готовый коннектор прямого копирования допустим только для таблиц с неизменной структурой.

## Компромиссы

CDC удерживает WAL и требует дискового резерва. Для каждой миграции нужны реальные объёмы и репетиция. Откат после внешних денежных операций имеет ограничения; безопаснее сохранить нового владельца и восстановить его работоспособность, чем повторить платёж из устаревшего состояния.
