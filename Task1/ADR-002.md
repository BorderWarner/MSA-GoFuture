# ADR-002. C2 To-Be, границы доменов и обратная совместимость

## Контекст

Кейс одновременно называет Yandex Cloud, EC2, RDS и AWS ELB/ALB. Принимается смешанная инфраструктура; точная исходная топология не предоставлена.

В исходной C3 Booking синхронно вызывает Driver, Pricing, Payments, Geography, Fraud и Notification. Несколько компонентов напрямую читают чужие таблицы. Payouts выделен в компонент, хотя отдельной продуктовой команды для него нет.

Мобильные клиенты обновляются не одновременно; активные поездки и платежи нельзя произвольно переносить между двумя реализациями.

## Требования

Доработать исходную C2 на основе ролей C1 и доменных компонентов C3. Показать восемь сервисов, владельцев данных, сохранённые интеграции и механизм обратной совместимости для поэтапной замены монолита.

## Решение

- Домены и владельцы данных: [SVG](svg/focus-c2-domain-ownership.svg) · [PNG](focus-c2-domain-ownership.png) · [PlantUML](sources/focus-c2-domain-ownership.puml).
- Outbox и перенос данных: [SVG](svg/focus-c2-outbox-migration.svg) · [PNG](focus-c2-outbox-migration.png) · [PlantUML](sources/focus-c2-outbox-migration.puml).

Допущение об исходном размещении: Django/Celery и PostgreSQL RDS размещены в AWS рядом с AWS ALB; в Yandex Cloud находятся аналитический контур ClickHouse/DataLens и часть платформенных инструментов. Их связь — резервированные частные VPN-каналы. C2 показывает логические контейнеры и их контракты; физическое размещение не меняет доменного владельца записи.

Входные приложения: пассажирское и водительское приложения, корпоративный портал и административный портал бухгалтера. Приложения получают токен в IAM по OIDC Authorization Code с PKCE. API Gateway загружает JWKS, проверяет подпись, `issuer`, `audience` и срок токена; роли берёт из проверенных claims, ограничивает нагрузку и направляет запрос к владельцу маршрута. Бизнес-сервисы Python/Django развёртываются независимо в Kubernetes; каждый хранит собственные данные и outbox. Kafka связывает домены, Debezium передаёт outbox; исключение — высокочастотная телеметрия Driver, которую Driver публикует напрямую с подтверждением брокера. IAM — Keycloak; наблюдаемость — Prometheus, Grafana, Loki, Alertmanager. PostgreSQL/RabbitMQ exporters уже присутствуют в исходном стеке: они читают статистику, Prometheus опрашивает их HTTP endpoint `/metrics`. Это отдельный путь наблюдения, а не передача бизнес-данных.

Временные контейнеры: фасад совместимости, монолит, старая БД, RabbitMQ/Celery и Python-процесс переноса данных. Legacy-домены публикуют бизнес-факты через outbox старой БД, чтобы уже выделенные Geography, Notification и Analytics получали изменения старых когорт. Для legacy-когорт сохраняются исходные платёжные, картографические и push-интеграции до передачи соответствующего домена. CI/CD Jenkins и Registry поставляют каждый сервис отдельно и не участвуют в пользовательском запросе.

### Назначение добавлений

| Добавление | Зачем введено и почему выбран этот способ |
|---|---|
| API Gateway | Одна точка проверки JWT, версии API и маршрута к старому/новому владельцу; правила миграции не приходится выпускать отдельно во всех клиентах |
| IAM / Keycloak | Общая выдача токенов и ролей для независимых доменов; готовый IAM отделяет жизненный цикл учётной записи от кода монолита |
| Фасад совместимости / Python | Переводит прежние DTO и ошибки в новый контракт, пока старые приложения и активные поездки продолжают работу |
| Booking, Driver, Pricing, Payments/Payouts, Notification, Geography, Analytics, Fraud | Восемь границ соответствуют командам и бизнес-инвариантам в таблице ниже; каждый домен можно выпускать и масштабировать отдельно |
| Booking DB, Driver DB, Pricing DB, Payments DB, Notification DB, Geography DB, Analytics metadata, Fraud DB | Отдельные PostgreSQL БД/роли закрепляют владение данными и схемой. Сохранение PostgreSQL снижает объём технологической миграции; физический сервер не обязан быть отдельным для каждой БД |
| Transactional outbox | Состояние и предназначенный к отправке бизнес-факт фиксируются одной PostgreSQL-транзакцией; потребитель не теряет факт из-за сбоя между commit и публикацией |
| CDC / Debezium | Читает outbox и WAL без периодического полного опроса таблиц; тот же стек помогает догнать snapshot при переносе больших данных |
| Kafka | Долговременный журнал позволяет разным доменам независимо читать события, восстанавливать проекции и повторять обработку; старые очереди Celery остаются в RabbitMQ |
| Перенос данных / Python | Применяет snapshot/CDC к новой схеме с versioned upsert и контрольными точками. Debezium доставляет изменения, но не определяет правила преобразования доменных данных |
| Kubernetes и независимые конвейеры поставки | Обеспечивают отдельный развёртывание, проверки работоспособности и горизонтальное масштабирование сервисов; Jenkins/Registry сохраняются из исходного стека |

Outbox — таблица внутри БД владельца, а не отдельный сетевой сервис. Например, Booking сохраняет заказ и BookingCreated в одной транзакции: при rollback нет обоих результатов, после commit временный отказ Kafka задерживает доставку, но не удаляет событие. Доставка CDC допускает повторы, поэтому у факта есть `event_id` и потребитель ведёт дедупликацию. Это решение требуется уже при первом выделении Notification/Analytics из монолита.

### Почему процесс координирует Booking

Booking владеет жизненным циклом поездки: созданием, назначением, отменой и завершением. Координатор — внутренний модуль этого домена; он хранит состояние процесса вместе с заказом и атомарно фиксирует переход и следующую команду в outbox. Driver самостоятельно решает, допустим ли резерв, Payments владеет денежными операциями, Fraud — результатом проверки: координатор не выполняет их локальные транзакции и не получает доступ к их БД.

У одного процесса поездки один активный обработчик, но экземпляров Booking может быть несколько: они распределяют разные поездки по ключу и восстанавливают незавершённые шаги из БД. Размещение координатора в Booking не означает один процесс на всю платформу. Причина выбора — общий владелец состояния заказа и процесса, а не экономия на отдельном имени сервиса.

### Преобразование исходной архитектуры

| Исходные C1–C3 | C2 To-Be |
|---|---|
| Пассажир, водитель, корпоративный менеджер, бухгалтер, разработчик и SRE | Все роли и четыре клиентских приложения сохранены отдельно |
| Django Monolith и девять доменных компонентов C3 | Восемь сервисов; Payouts входит в Payments как часть общего ledger |
| Общий PostgreSQL RDS и прямые SQL между доменами | Отдельные БД владельцев; исходная БД остаётся только у монолита на время переноса |
| Redis и Elasticsearch | Сохранены отдельно: доменные кеши по ACL и геоиндекс Geography |
| RabbitMQ и Celery | Сохранены отдельно для старых задач до их дренирования; новые факты идут через outbox/CDC и Kafka |
| Spark/Flink, ClickHouse, DataLens | Сохранены отдельными контейнерами; Analytics владеет обработкой и витринами |
| Prometheus, Grafana, Loki, Alertmanager | Сохранены отдельными контейнерами, распространяются на независимые сервисы |
| Jenkins, CI/CD Workers, Docker Registry | Сохранены; сборка и поставка становятся независимыми по сервисам |
| Яндекс Пэй, Яндекс Карты, FCM, APNs, Huawei Push Kit, API банка | Сохранены отдельными интеграциями; владельцы — Payments, Geography и Notification |

Шлюз, IAM и фасад совместимости добавлены перед доменными API и монолитом. C2 сохраняет исходные идентификаторы контейнеров; изменены владельцы связей после декомпозиции. Внешние локальные PSP и карты подключаются теми же адаптерами владельцев.

### Домены и владельцы данных

| Сервис / команда | Собственные данные и инварианты | Контракт и интеграции |
|---|---|---|
| Booking | Заказ, поездка, история состояний, корпоративный заказ, состояние Saga. Один активный переход версии поездки | REST: создать/отменить/завершить поездку; события BookingCreated, TripCompleted. Команды резервирования Driver и Payments |
| Driver | Профиль водителя, разрешение работать, доступность, резервирование и последняя принятая позиция. Один действующий резерв водителя | REST приём координат; DriverLocationUpdated, DriverReserved, DriverReleased. Обновления через CAS версии резерва |
| Pricing | Тарифы, quote с TTL, версия алгоритма, действующие коэффициенты | REST quote; PriceUpdated. Собственная проекция спроса/предложения, без запроса чужих БД |
| Payments | Авторизации, списания, ledger, возвраты, выплаты и сверки. Payouts — модуль внутри Payments | Команды AuthorizePayment, CapturePayment, VoidAuthorization, RefundPayment; адаптеры Яндекс Пэй, локальных PSP и банков |
| Notification | Устройства, каналы, шаблоны, история попыток доставки | Подписки на события; FCM для Android, APNs для iOS, Huawei Push Kit |
| Geography | Зоны, маршруты, геопроекция доступных водителей | API кандидатов и маршрутов; Яндекс Карты и локальные карты. Elasticsearch — восстанавливаемый индекс |
| Analytics | Обезличенные/разрешённые события, витрины, наборы признаков и версии моделей | Подписки на события всех доменов; ClickHouse, DataLens, ML. Владельцы исходных данных сохраняют право определять использование |
| Fraud | Правила риска, признаки, решения и разбор случаев | FraudApproved/FraudRejected; собственная событийная проекция, без чтения таблиц Payments |

Каждый операционный сервис имеет собственную БД и учётные данные. Физический PostgreSQL-кластер может обслуживать несколько БД одного контура, но междоменные JOIN и запись чужим пользователем запрещены. Redis разделён ACL и пространствами ключей между доменами; доступ между партнёрами запрещён. Elasticsearch принадлежит Geography. Analytics владеет ClickHouse; операционные сервисы не используют его как транзакционную БД.

Tenant — контур партнёра. Все сущности содержат `tenant_id`, `home_region`, собственный идентификатор и версию. Корпоративный клиент — организация внутри tenant партнёра, а не отдельный партнёр. Ссылки между доменами — идентификаторы и локальные проекции; междоменных foreign key нет. IAM, шлюз, конфигурация и подключение партнёров принадлежат Platform.

Booking получает у Geography список кандидатов и спрос по зонам, затем выбирает водителя по ETA, дефициту соседних зон и ограниченному ожиданию. Geography не резервирует водителя: только Driver атомарно принимает резерв. Pricing использует спрос/предложение; Driver не рассчитывает тариф, Payments получает зафиксированную стоимость и ведёт взаиморасчёты.

### Обратная совместимость

Применяется Strangler Fig: шлюз направляет запросы по версии API, tenant, региону и когорте к старой или новой реализации. Фасад переводит старые DTO и ошибки в новый контракт, но не содержит новой бизнес-логики. Существующая поездка несёт `execution_owner`; переходы всегда идут к тому же владельцу до терминального состояния. Таблица маршрутизации версионируется и кешируется локально; при её недоступности действует последняя подтверждённая версия.

| Изменение | Правило совместимости | Проверка |
|---|---|---|
| REST | `/v1` сохраняет поля и семантику; новое обязательное поле только в `/v2`; Idempotency-Key у изменяющих запросов | Consumer-driven проверки старых мобильных и корпоративных клиентов |
| События | Добавление необязательных полей; несовместимая семантика — новый тип/версия и миграция подписчиков | Схемы и контрактные примеры прежних потребителей |
| Схема БД | Expand → совместимый код → backfill → проверка → contract после отключения кода, использующего прежнюю схему | Прогон миграций на копии; запрет удаления используемого поля |
| Маршрут | Canary новых заказов 1% → 5% → 25% → 100%; по 24 часа наблюдения вне пиков, если хватает выборки | Нет роста ошибок/latency, расхождений состояния и дублирующих внешних операций |
| Legacy-клиент | Фасад сохраняется до отсутствия обращений 30 дней и окончания объявленного срока поддержки | Метрики версии приложения/API без идентификаторов пользователей в метках |

Shadow-режим разрешён для чтений и расчётов. Платежи, выплаты и отправка уведомлений в shadow-ветке не выполняются. При превышении бюджета ошибок новые заказы возвращаются на допустимый путь, уже начатые остаются у своего владельца.

## Альтернативы

**Отдельный Trip Orchestrator или универсальный workflow-сервис.** Он позволил бы независимо выпускать и масштабировать координацию, но состояние заказа осталось бы в Booking: каждый переход потребовал бы согласования двух владельцев и дополнительной защиты от расхождений. Для одного доменного процесса это лишняя граница; выделение оправдано, если появятся несколько независимых междоменных процессов, отдельная команда и измеренная потребность в другом цикле поставки. В выбранном варианте координатор остаётся модулем Booking.

**Модульный монолит, сервис на таблицу или отдельный Payouts.** Модульный монолит полезен для подготовки границ, но сохраняет общий выпуск и масштабирование. Сервис на таблицу дробит бизнес-инварианты, а отдельный Payouts без своей команды разделяет один ledger с Payments; выбраны восемь доменов и БД с отдельными правами вместо общего SQL-пользователя.

**Прямая маршрутизация клиентов и немедленная замена API.** Правила перехода пришлось бы синхронно обновлять в четырёх приложениях, включая давно установленные мобильные версии. Gateway и временный Python-фасад сохраняют прежний контракт; самописная выдача токенов в каждом домене отклонена в пользу Keycloak, чтобы не дублировать управление пользователями и проверку ролей.

**Публикация после commit, polling outbox или полное event sourcing.** Первая схема теряет событие при сбое процесса после commit; polling с надёжным подтверждением допустим, но создаёт дополнительный опрос и отдельный механизм доставки. Выбран outbox с Debezium, уже нужным для переноса WAL; event sourcing потребовал бы переработать всю модель хранения вместо поэтапного отделения Django-доменов.

**Существующие очереди RabbitMQ/Celery или RabbitMQ Streams.** Очереди остаются для старых заданий; Streams мог бы обеспечить журнал и replay, но потребовал бы отдельного выбора интеграций CDC и аналитики. Kafka выбран для общего журнала с Debezium и существующим Flink; PostgreSQL сохранён вместо одновременной смены СУБД. Docker Compose на общей VM отклонён для целевого runtime из-за требуемого независимого масштабирования и автоматического переразмещения сервисов.

## Компромиссы

Kubernetes добавляет операционную нагрузку: его сопровождение закрепляется за Platform и SRE.

Проекции согласуются с задержкой. Доступность водителя подтверждается только ответом Driver, цена — действующим quote, баланс — Payments. Неактуальный индекс не даёт права совершить транзакцию.

Фасад требует контрактных проверок и срока удаления. Возврат трафика не равен откату данных: после передачи права записи применяется процедура [ADR-004](ADR-004.md).
