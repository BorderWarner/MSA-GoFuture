# ADR-015. Мультитенантная платформа и подключение партнёров

## Контекст

GoFuture планирует запускать партнёров в новых регионах за 2–4 недели. Общая платформа должна поддерживать разные настройки продукта и изолировать данные партнёров.

## Требования

Определить модель изоляции, IAM с корпоративным SSO, автоматизированное подключение и мониторинг по партнёрам. Подключение должно восстанавливаться после частичного сбоя и открывать пользовательский доступ только после проверки готовности.

### Изоляция данных

Tenant — партнёрский контур одного рынка с отдельной политикой размещения данных. Международный партнёр может иметь несколько tenant; права между ними автоматически не объединяются. Корпоративный клиент такси относится к `corporate_account_id` внутри tenant.

Для каждого tenant разворачиваются сервисы из общего образа в отдельном namespace, собственные IAM, потоковые обработчики и ML. Общая физическая инфраструктура допускается при отдельных учётных данных, сетевых ограничениях и квотах. При требовании физической изоляции выделяется отдельный кластер или облачный проект.

| Слой | Граница изоляции |
|---|---|
| API и сервисы | Tenant определяется доверенным `issuer` и доменом из каталога. Gateway и домены проверяют tenant, роль и принадлежность объекта; пользовательский заголовок не меняет контекст. Workload identity и default-deny NetworkPolicy ограничивают связи |
| PostgreSQL | Отдельная БД и роль на пару tenant × домен; приложения не имеют superuser и доступа к соседним БД |
| Redis / Elasticsearch | Отдельный экземпляр Redis tenant; индексы Elasticsearch с точными grants. Префикс ключа сам по себе не считается изоляцией |
| Kafka / Registry / DLQ | Топики `gf.<region>.<tenant>...`, отдельные principals, ACL и квоты. Registry ограничивает пространства схем. Consumer сверяет tenant события, топика и своей identity; retry и replay сохраняют эти ограничения |
| Object Storage и ML | Buckets, роли, ключи чувствительных данных, MLflow и модели принадлежат tenant; чужие обучающие данные и модели не используются |
| ClickHouse / BI | БД, пользователи и разрешённые views tenant. В Yandex Cloud передаются только согласованные агрегаты в отдельную BI-БД tenant; DataLens ограничивает datasets и подключения |
| IAM | Отдельное развёртывание Keycloak и БД каждого tenant; корпоративный IdP выдаёт идентичность, локальные правила определяют права |
| Наблюдаемость | Collector назначает tenant по workload identity и удаляет PII/токены. Query gateway ограничивает каждый запрос к региональным хранилищам |
| Резервные копии / DR | Физический PostgreSQL-кластер объединяет только одну группу восстановления с одинаковой политикой размещения. Восстановление не выдаёт партнёру общий snapshot; перед открытием повторно применяются удаления |

Каталог хранит UUID tenant, разрешённые регионы, текущий регион записи, версии политики/конфигурации, квоты, статус и ссылки на секреты. Секреты и бизнес-данные находятся в своих региональных хранилищах. Сервис подключается только к БД своего tenant; callback платёжного провайдера сопоставляется по зарегистрированному merchant reference и проверенной подписи.

Репликация, fencing и переключение группы восстановления выполняются по [ADR-009](../Task3/ADR-009.md) и [ADR-011](../Task3/ADR-011.md). Общий дисковый ключ кластера не считается отдельным ключом БД tenant; для чувствительных полей применяется шифрование ключом tenant. Доступ инфраструктурного администратора к содержимому данных требует отдельного временного разрешения и аудита.

### Автоматизированное подключение

Platform IAM обслуживает заявителя и сотрудников платформы до создания IAM партнёра. Все публичные входы идут через региональный LB/WAF. Onboarding Service принадлежит Platform и хранит состояние процесса в PostgreSQL; команды и конфигурация доставляются через outbox в control topics существующей Kafka.

| Этап | Действие и результат |
|---|---|
| `SUBMITTED` → `REVIEW` | Заявитель передаёт компанию, рынок, домен, IdP и профиль нагрузки. Сохраняются заявка и ключ идемпотентности |
| `REVIEW` → `APPROVED` / `REJECTED` | Оператор проверяет заявку; DPO согласует категории данных, размещение и DR, SRE — ёмкость и квоты |
| `APPROVED` → `PROVISIONING` | Резервируется UUID tenant; создаются namespace, БД и роли доменов, Redis, Kafka/ACL, buckets/ключи, аналитика, ML и мониторинг |
| `PROVISIONING` → `IAM_READY` | Создаются отдельное развёртывание Keycloak и его БД; затем realm, роли, клиенты и SSO с проверенным IdP партнёра |
| `IAM_READY` → `CONFIGURED` | Применяются тарифы, флаги функций, региональные провайдеры и ссылки на секреты; интеграции проверяются в тестовой среде |
| `CONFIGURED` → `VALIDATING` | Проверяются изоляция, SSO, сценарий поездки, мониторинг и готовность разрешённого DR |
| `VALIDATING` → `ACTIVATING` | Публикуется ConfigPrepared. Gateway, все обязательные домены и IAM config agent применяют одну версию при закрытом пользовательском входе и возвращают ACK |
| `ACTIVATING` → `ACTIVE` | После всех ACK сохраняются `ACTIVE` и событие TenantActivated. Gateway открывает вход только при совпадении версии и readiness |
| Ошибка → `RETRYING` / `FAILED` | Повторяется незавершённый шаг; после ограниченных попыток требуется разбор оператором. Пользовательский вход остаётся закрытым |

C3 разделяет API заявки, координатор процесса, адаптеры ресурсов/IAM, проверки и обработчик outbox. Адаптеры запоминают созданные ресурсы и перед повтором проверяют результат предыдущей операции. Одинаковая заявка не создаёт второй tenant. Компенсация удаляет только пустые ресурсы этой заявки и отзывает доступ; действующие финансовые операции и аудит не удаляются. Цель технического подключения после согласований — до 60 минут; юридическая проверка учитывается отдельно.

Перед активацией проверяются запреты tenant A → B для API, БД, кеша, Kafka, объектов, моделей и BI; отказ при чужом `issuer`/роли; повтор заявки и восстановление после сбоя шага. Проверяются также финансовые полномочия, доставка алертов и готовность DR. Это условия приёмки дизайна, требующие проверки при реализации.

Действующие tenant используют локальную подписанную конфигурацию при недоступности Onboarding Service. Отзыв прав и аварийное переключение выполняются критическим контуром независимо от подключения новых партнёров. При закрытии tenant прекращаются новые операции, завершаются обязательства и применяются правила хранения/удаления.

### Мониторинг мультитенантного окружения

Сохраняется стек Task2: Prometheus, Grafana, Alertmanager, OTel Collector, Loki, Tempo и exporters. Kafka Exporter измеряет consumer lag по смещениям; JMX exporters — состояние брокеров и CDC. Prometheus собирает также метрики Registry, Collector, authority и доставки Alertmanager. Сбор и алертинг региональны.

| Область | Метрики / начальные условия алерта | Ответственный и действие |
|---|---|---|
| Критический путь | Ошибки, задержка и burn rate отдельно по tenant/региону; 14,4 на окнах 5 мин/1 ч либо 6 на 30 мин/6 ч | SRE и доменная команда: инцидент, остановка развёртывания |
| IAM / изоляция | Ошибки login/refresh, отказы авторизации, межтенантные проверки; login failure >5% за 5 мин | Platform: проверка причины; успешный запрещённый доступ — немедленная изоляция и отзыв прав |
| Ресурсы | CPU/memory, DB pool, Kafka lag/quotas, возраст очередей, заполнение хранилищ | SRE: квоты и масштабирование; пик одного tenant не вытесняет остальных |
| Onboarding | Длительность этапов, ошибки, повторы, оставшиеся ресурсы; подключение >60 мин после согласований | Оператор: разбор заявки; массовый сбой адаптеров — оповещение Platform |
| Данные / ML | Свежесть, карантин, drift, пропуски признаков и версия модели | Data-команда: правила Task4, остановка публикации или резервные правила |
| Телеметрия / аудит | Потерянные сигналы, ошибки доставки алертов, отсутствие аудита >60 с | SRE/Platform: восстановление наблюдаемости; недоступность финансового аудита блокирует привилегированные изменения |

SLO 99,99% наследуется из Task3: считается отдельно по tenant/региону и критическому маршруту, включая вход и refresh. Усреднение платформы не скрывает отказ небольшого партнёра. Для малой нагрузки добавляются синтетические проверки. Пороги уточняются после нагрузочных испытаний.

Метки метрик ограничены tenant, регионом, сервисом и фиксированными классами маршрутов/ошибок; идентификаторы пользователей и поездок в них не включаются. Партнёр получает отдельный экземпляр Grafana с OIDC своего IAM. Источник данных Grafana обращается к Query gateway с учётными данными своего tenant. Query gateway ограничивает запросы PromQL/LogQL/TraceQL, поиск меток и получение трасс по ID; неизвестные запросы и прямой доступ к хранилищам запрещены. Организация или переменная панели не заменяет этот контроль.

Платформенная Grafana сохраняется для SRE с отдельными полномочиями: агрегаты доступны постоянно, подробности — по временной роли в разрешённом регионе. Alertmanager отправляет уведомления ответственным без персональных данных.

### Кастомизация

Партнёр настраивает брендинг, язык, валюту, часовой пояс, классы поездок, тарифные пределы, зоны, флаги функций и проверенные адаптеры локальных PSP, банков, карт и push. Значения проходят схему и проверки доменных владельцев; финансовые изменения требуют согласования.

Конфигурация версионируется и применяется постепенно с контролем ошибок. Активная поездка сохраняет свою версию тарифа и условий; откат конфигурации не отменяет исполненный платёж. Регионы хранения, роли платформы и обязательные проверки безопасности не отключаются настройками партнёра.

## Альтернативы

**Общие таблицы с RLS.** Экономят ресурсы, но требуют правильного tenant-контекста во всех запросах и фоновых обработчиках. Выбраны отдельные БД и экземпляры сервисов каждого tenant для независимых учётных данных и обновлений; физические кластеры остаются общими в пределах разрешённой группы восстановления.

**Готовый движок процессов.** Temporal может упростить развитие сложных процессов, но добавляет отдельную систему эксплуатации. Для подключения партнёра выбран координатор на существующих PostgreSQL/Kafka с сохранением шагов и идемпотентными адаптерами.

**Отдельные хранилища телеметрии каждого tenant.** Упрощают изоляцию, но увеличивают стоимость. Выбраны региональные хранилища с Query gateway; отдельные хранилища потребуются, если он не обеспечивает ограничения для всех разрешённых запросов.

## Компромиссы

Число партнёров в кейсе не задано. При T tenant нужны как минимум 8 × T развёртываний доменных сервисов и 8 × T доменных БД, а также отдельные IAM и ML-компоненты tenant. Реплики и разрешённый DR учитываются дополнительно. Общие узлы и кластеры снижают накладные расходы, но не отменяют этого роста. Перед подключением очередной группы SRE проверяет квоты, резерв и стоимость на 1000 поездок; снижение затрат на 40% остаётся целью, которую нужно подтвердить расчётом ёмкости.

Обновления выполняются волнами. Автоматизация сокращает технические операции, но не сроки договоров и проверки провайдеров. Новая функция вне схемы настроек добавляется в общий продукт, без отдельного форка партнёра.
