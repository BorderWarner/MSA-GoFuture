# ADR-010. Схема геомаршрутизации

## Контекст

Ближайший регион не всегда имеет право обрабатывать данные tenant. Поездка должна сохранять владельца даже при смене сети пользователем.

## Требования

Показать выбор ближайшего разрешённого региона, закрепление записи за владельцем, маршрутизацию при отказе и ограничения передачи данных.

## Решение

Схема маршрутизации: [SVG](svg/geo-routing.svg) · [PNG](geo-routing.png) · [PlantUML](sources/geo-routing.puml).

Bootstrap DNS направляет к ближайшей региональной точке входа; в DNS и публичном bootstrap нет профиля, координат или токенов. Для партнёрского домена заранее задаётся разрешённый набор endpoint. Два независимых авторитетных DNS-провайдера получают одну версионированную подписанную конфигурацию; TTL 30 с — целевое значение, не гарантия поведения рекурсивного кеша.

Региональный Gateway проверяет `issuer`, tenant и подписанный routing token с `home_region`/epoch. При подключении tenant его `home_region` выбирается из разрешённых регионов с учётом обслуживаемого рынка и RTT. Новая поездка наследует текущий write-region tenant; географическая близость не даёт второму региону право записи. Для существующей поездки используется её owner с учётом завершённого failover. Партнёр с независимыми рынками получает отдельный tenant на рынок; объединение таких tenants допустимо только в разрешённой отчётности. Пользователь, попавший на неподходящий endpoint, получает разрешённый региональный адрес до отправки тела с PII; SDK повторяет запрос с тем же Idempotency-Key.

Health-check внешней доступности отделён от readiness записи: последняя проверяет epoch/lease, доступность БД, Kafka и допустимость обработки данных.

Подписанный список двух разрешённых endpoint кешируется SDK. При сбое первичного endpoint клиент проверяет резерв с коротким timeout и jitter; сервер резервного региона принимает изменяющий запрос только после продвижения данных. Это сокращает зависимость от DNS TTL. Старые клиенты без такой логики переключаются по DNS и могут превысить целевой RTO; их поддержка ограничивается миграционным периодом Task1.

## Альтернативы

**Только GeoDNS по IP и малый TTL.** Это не учитывает право региона обрабатывать tenant и не управляет чужим DNS-кешем. Выбраны DNS/bootstrap для первого адреса и подписанный список endpoints в SDK; изменяющий запрос всё равно проверяется по текущему региону записи.

**Один глобальный reverse proxy, например общий edge для всех payload.** Он упростил бы переключение клиента, но стал бы точкой обработки чувствительных тел вне регионального контура. Выбран региональный HTTPS-вход и адресный повтор SDK до отправки PII в неподходящий регион.

**Закрепить все запросы навсегда за исходным регионом.** Это сохраняет простую модель владения, но лишает платформу регионального восстановления. Смена endpoint допускается только после проверенного продвижения данных, с тем же Idempotency-Key и новой версией маршрута.

## Компромиссы

SDK требует совместимого обновления. Устаревший DNS может продолжать выдавать недоступный регион; серверное ограждение записи остаётся обязательным. Трансграничный failover запрещён, пока политика не разрешает обработку в резерве.
