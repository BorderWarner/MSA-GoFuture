# ADR-008. Регионы развёртывания и защита C2

## Контекст

Исходная инфраструктура смешанная: AWS ALB, EC2 и RDS обслуживают монолит, Yandex Cloud — аналитические и платформенные инструменты. Исходное размещение принято в [ADR-002](../Task1/ADR-002.md). Для новых рынков требуется дополнительный провайдер.

Открытие новых регионов увеличивает число публичных входов и служебных соединений.

## Требования

Обосновать размещение более чем в трёх географических регионах для 99,99% доступности и низкой задержки в Юго-Восточной Азии и Южной Америке. Доработать C2 событийной платформы, добавить WAF, firewall и смежные средства защиты.

## Решение

### Провайдеры, регионы и ёмкость

Новые международные контуры развёртываются в Google Cloud: один дополнительный провайдер даёт две региональные пары рядом с целевыми рынками. Регионы и зоны выбраны по документации Google Cloud «Compute Engine regions and zones».

| Код проекта | Регион Google Cloud | Зоны | Основная нагрузка | Плановый резерв |
|---|---|---|---|---|
| SG | asia-southeast1, Сингапур | a, b, c | Сингапур и разрешённые рынки ЮВА | JKT при одобренной передаче |
| JKT | asia-southeast2, Джакарта | a, b, c | Индонезия, локальные карты/PSP | SG при одобренной передаче |
| SAO | southamerica-east1, Сан-Паулу | a, b, c | Бразилия | SCL при одобренной передаче |
| SCL | southamerica-west1, Сантьяго | a, b, c | Чили и разрешённые соседние рынки | SAO при одобренной передаче |

Сингапур/Джакарта уменьшают межконтинентальные обращения в ЮВА, Сан-Паулу/Сантьяго дают два независимых региона в Южной Америке. Четыре региона одновременно обслуживают собственные tenant/города; один заказ имеет только один регион записи. Пары не означают автоматическое правовое разрешение переноса данных.

В каждом регионе — собственный regional GKE-кластер, control plane и node pools по трём зонам, минимум три реплики критического stateless-сервиса с anti-affinity и PodDisruptionBudget. PostgreSQL, Kafka и ClickHouse имеют отдельные выделенные node pools/VM и дисковые квоты; HA PostgreSQL управляется Patroni, его DCS локален региону. Нет общего WAN Kubernetes-кластера или растянутого Kafka quorum.

Плановый нормальный пик: по 150 тыс. из 600 тыс. поездок на регион. Регион должен держать **300 тыс. поездок** при потере своего парного региона. SRE резервирует квоты, warm capacity, диски и broker bandwidth заранее; отказ не ждёт закупки VM. HPA реагирует на latency/CPU и lag, Cluster Autoscaler расширяет неаварийный запас. При неравномерном рынке sizing выполняется по большей из местной и принимаемой нагрузок; деление на четыре — только исходное допущение.

Цели для измерений: пользователь → регион RTT p95 ≤100 мс для выбранных городов; цена end-to-end p95 ≤400 мс, принятие заказа ≤600 мс. При failover допускается до 700 мс, если бизнес согласует деградацию. География сама по себе таких задержек не доказывает: нужны пробы из мобильных сетей городов и замеры до PSP.

Legacy-когорты остаются в AWS до миграции по плану Task1. Региональные кеши подписанных образов и конфигурации позволяют работать при недоступности центрального CI/CD.

### Защита

Основная схема C2: [SVG](svg/c2-global.svg) · [PNG](c2-global.png) · [PlantUML](sources/c2-global.puml).

Полная схема C2 (full): [SVG](svg/c2-global-full.svg) · [PNG](c2-global-full.png) · [PlantUML](sources/c2-global-full.puml).

Защищённые соединения к БД и Kafka: [SVG](svg/focus-c2-private-security.svg) · [PNG](focus-c2-private-security.png) · [PlantUML](sources/focus-c2-private-security.puml).

VPC firewall ограничивает доступ к БД и Kafka по исходному workload и порту. Для PostgreSQL разрешён TCP 5432 владельцу, его CDC, процессу переноса и exporter с отдельной read-only ролью; для Kafka — настроенный TLS listener 9093 разрешённым producer/consumer. Redis и Elasticsearch разрешают соединения только своим доменным клиентам на настроенных TLS endpoints. JMX доступен только локальному exporter, наружу публикуется его /metrics для Prometheus. Административные операции выполняются отдельной scoped identity через контролируемый канал; обычные приложения таких разрешений не получают. Внутри GKE действует дополнительная NetworkPolicy. Модель сетевых правил описана в документации Google Cloud «VPC firewall rules».

Рабочий HTTPS идёт клиент → LB → Gateway либо IAM; обход LB к backend запрещён сетевыми правилами. WAF применяется к backend services API и OIDC. Egress proxy — отдельный обработчик рабочего исходящего трафика; прямые внешние вызовы сервисов и legacy запрещены. Сочетание механизмов описано в документации Google Cloud по интеграции Cloud Armor.

| Механизм | Назначение и размещение |
|---|---|
| Региональный HTTPS LB + Cloud Armor | TLS-терминация и WAF в регионе, правила SQLi/XSS, ограничение частоты; изменения сначала в preview. Региональные backend policies поддерживаются официально |
| VPC firewall / private subnets | БД и Kafka без публичных адресов; inbound только от разрешённых workload и health-check; доступ администраторов через контролируемый канал |
| Kubernetes NetworkPolicy | Default deny между namespace, точечные разрешения Gateway → API, CDC → БД/Kafka, обработчики → собственные хранилища |
| TLS/mTLS и workload identity | Проверка сервиса-получателя и служебной учётной записи; пользовательский JWT не заменяет сервисную авторизацию |
| Egress proxy / allowlist | Разрешены только нужные PSP, банки, карты, push и DR; журналировать отказ без записи секретов |
| KMS / Secret Manager | Региональные ключи, отдельные ключи tenant для чувствительных данных, ротация; секреты не хранятся в образах/событиях |
| Аудит / резервные копии | Изменения ролей, маршрутов и ключей отдельно от логов запросов; неизменяемые резервные копии, отдельные полномочия удаления |

Маршрутизация описана в [ADR-010](ADR-010.md), аварийное переключение — в [ADR-011](ADR-011.md).

### Размещение аналитики

Региональные ClickHouse-витрины передают в сводную витрину Yandex Cloud только разрешённые статистические агрегаты для DataLens. Публикация BI читает read-only views; персональные строки, платёжные reference и точные координаты не экспортируются. Отказ центрального BI не блокирует поездки. Состав экспорта, доступ получателей и риск повторной идентификации контролируются по [ADR-012](ADR-012.md).

Аудит и резервные копии используют разные buckets, права и сроки хранения.

## Альтернативы

**Только Yandex Cloud или расширение текущего AWS через Local Zone Santiago.** Первый вариант не даёт выбранных четырёх регионов рядом с рынками кейса. AWS Local Zone Santiago связана с родительским us-east-1 и не эквивалентна самостоятельному трёхзонному DR-региону Южной Америки. Выбран Google Cloud с SG/JKT и SAO/SCL; вариант AWS с другим полноценным набором регионов остаётся пересматриваемым, но не подменяется Local Zone.

**WAF как единственная защита или единый универсальный firewall-прокси.** WAF работает с HTTP, а БД/Kafka и межсервисные права требуют других уровней контроля. Выбраны распределённый VPC firewall и NetworkPolicy/mTLS; отдельный сетевой прокси на каждом SQL-вызове добавил бы общий узел отказа без необходимости.

**Самостоятельная эксплуатация WAF и хранилища секретов.** Возможна, но увеличивает число обслуживаемых критических компонентов. Для новых регионов выбраны средства провайдера.

**Прямой доступ DataLens к региональным данным.** Отклонён, чтобы ограничить трансграничную передачу проверенными агрегатами.

## Компромиссы

Резервная ёмкость, межрегиональный трафик и три провайдера на время миграции увеличивают стоимость и сложность эксплуатации. Резервирование регионов одного провайдера не защищает от полного отказа его глобальных сервисов; этот остаточный риск учитывается в бюджете доступности.

Ошибочное правило WAF/firewall может вызвать отказ; нужны canary, тесты разрешённых потоков и быстрый откат политики. mTLS добавляет управление сертификатами и наблюдение за сроком действия.
