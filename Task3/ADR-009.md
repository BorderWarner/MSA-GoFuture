# ADR-009. Схема репликации данных

## Контекст

В Task2 Kafka и БД региональны. Потеря региона требует восстановить состояния Saga, idempotency ledger и смещения без двух активных владельцев.

## Требования

Показать репликацию между выбранными регионами для каждого типа данных; определить владельца записи, допустимый DR, RPO и восстановление после переключения.

## Решение

Схема репликации: [SVG](svg/replication.svg) · [PNG](replication.png) · [PlantUML](sources/replication.puml).

Разрешённые направления: **SG → JKT, JKT → SG, SAO → SCL, SCL → SAO**. Встречные потоки принадлежат разным когортам и непересекающимся allowlist топиков; отражённая копия никогда не зеркалируется обратно. Каждый из четырёх регионов обслуживает собственные когорты и хранит резерв парных.

| Класс | Внутри региона | Между разрешёнными регионами | Цель RPO / восстановление |
|---|---|---|---|
| Все восемь доменных PostgreSQL БД, включая резервы Driver, ledger Payments, а также IAM/tenant config | Primary + синхронный standby другой зоны, третий standby; `synchronous_commit=on` | Асинхронный WAL кластера в standby парного региона, включая inbox/outbox; кластер объединяет только tenants с одинаковой политикой размещения | Локальный отказ: 0 подтверждённых транзакций; регион: ≤5 с при здоровой репликации. Для платежей обязательна сверка неопределённых операций |
| Kafka facts/commands | RF=3 по зонам, min ISR=2 | MirrorMaker 2 по allowlist топиков tenant, origin prefix сохраняется; обратная репликация этих же топиков запрещена | Цель lag ≤5 с; replay outbox закрывает пробелы, inbox убирает повторы |
| Location | RF=3, retention 6 ч | Репликация только разрешённым tenant; после отказа запрос свежей позиции устройству | До 5 с при здоровой репликации; старые координаты не используются для назначения |
| Redis / Elasticsearch | Реплики по зонам | Перестройка из Kafka и доменных источников | Кеш — не источник истины; 10 мин для полного прогрева, критический минимальный набор ≤60 с |
| Raw, checkpoints, модели, резервные копии | Региональные buckets, versioning, контроль доступа | Асинхронная копия в явно разрешённый bucket пары; отдельные ключи и политики | Raw/checkpoints ≤60 с; резервные копии ≤15 мин при WAL-архивировании, восстановление ≤4 ч |
| ClickHouse | Реплики по зонам, идемпотентная загрузка | Разрешённые факты/агрегаты, восстановление из raw и Kafka | Витрины ≤15 мин; потеря витрины не блокирует поездки |
| Метрики / логи / трассы | Локальные хранилища, alert rules в регионе | Агрегированные SLI; raw telemetry только по политике tenant | Трассы ≤60 с; финансовый аудит хранится отдельно от семплируемой телеметрии |

Асинхронный WAL через WAN допускает потерю подтверждённых локальных транзакций при отказе региона. Целевой RPO ≤5 с контролируется по durable LSN и heartbeat. При превышении порога удалённый standby теряет автоматическую готовность; при длительном отставании новые финансовые операции ограничиваются, а увеличение потенциальной потери объявляется инцидентом.

Один tenant может иметь несколько доменных БД, но его write-region переключается как согласованная группа всех доменных БД и IAM/конфигурации. Приоритет готовности — Booking, Driver reservation и Payments; остальные владельцы также должны быть восстановлены до открытия зависящих от них операций.

Согласованность между доменами восстанавливается событиями/Saga; общей транзакции всех БД нет. Из-за неодинакового lag после failover выполняются инварианты и сверка с PSP. Неподтверждённые/утраченные в пределах RPO запросы восстанавливаются по клиентским Idempotency-Key и внешним reference. Водители из неопределённого окна не выдаются на новое назначение до сверки с клиентом/Booking; истечение TTL освобождает только неподтверждённый резерв, но не водителя с возможной активной поездкой; один лишь пустой резерв на отставшей реплике не означает свободу водителя. Платёжный `operation_id` детерминирован устойчивыми `booking_id`, видом операции и ID бизнес-поручения, сохранённым инициатором, поэтому потеря локального inbox не создаёт нового ключа PSP.

### Kafka: переключение SG → JKT

Пример для tenant `t1`; тот же порядок применяется к каждому stream из allowlist. Используется MM2 `DefaultReplicationPolicy`, alias исходного кластера — `sg`.

| Этап | Публикация | Чтение |
|---|---|---|
| До отказа | SG: `gf.sg.t1.booking.events.v1` | Основные потребители читают SG; MM2 создаёт в JKT `sg.gf.sg.t1.booking.events.v1` |
| После fencing, до readiness | MM2 для этой когорты остановлен; фиксируются конечные смещения зеркала по партициям | Потребители DR дочитывают зеркало до зафиксированной границы; новые внешние команды ещё закрыты |
| После восстановления | JKT: `gf.jkt.t1.booking.events.v1`; outbox сохраняет исходные `event_id` и `region_id`, новые события имеют origin JKT | Потребители читают новый локальный топик; зеркало остаётся только для сверки и ограниченного replay |

Топики, ACL, схемы и конфигурация подписок создаются заранее; для DR выделены отдельные группы потребителей. Сопоставленные смещения служат ориентиром: чтение начинается с проверенной более ранней позиции, а при отсутствии надёжного checkpoint — с начала сохранённого журнала. Inbox/`event_id` и версии агрегатов устраняют повторный эффект; устаревшие команды отклоняются по `deadline`/`routing_epoch`. Для каждого stream фиксируется своя граница; незавершённые Saga восстанавливаются по БД и событиям, общей транзакции между топиками нет.

CDC в JKT запускается после продвижения БД с позиции, подтверждённой относительно восстановленной БД. Если сохранность replication slot/offset не доказана, retained outbox перечитывается явно с дедупликацией, без пропуска неопубликованного хвоста. После дочитывания зеркала потребители обрабатывают этот replay в новых локальных топиках; только затем проверяется readiness. Retention outbox покрывает максимальный срок восстановления и сверки. Продвижение запрещено, если недостающую историю нельзя восстановить в допустимом RPO.

Flink использует скопированный checkpoint только при совместимых входных топиках и смещениях; иначе восстанавливает state replay. До готовности производных сигналов действует последний безопасный тариф из Pricing DB; результаты публикуются с новой `revision` после сверки. Время replay измеряется под аварийной нагрузкой: превышение бюджета блокирует обещание RTO 120 с для этой когорты.

При плановом failback новые JKT-origin topics реплицируются в восстановленный SG по отдельному allowlist. Старые `sg.*` зеркала исключены, поэтому цикл не возникает. Возврат выполняется с новой границей и epoch после сверки; имена существующих событий не переписываются.

### Границы восстановления и резервные копии

Физическая WAL-репликация и полная резервная копия охватывают весь кластер, без фильтрации отдельных БД. Партнёры с разными разрешёнными DR-регионами получают отдельные кластеры; смена политики требует переноса данных перед включением нового направления. Правило применяется также к IAM и хранилищу резервных копий.

Единица физического переключения — группа восстановления (recovery cohort): tenant с одинаковыми основным и резервным регионами и политикой размещения. PostgreSQL-кластеры обслуживают только БД этой группы. При потере основного экземпляра БД согласованно переключаются все её tenant. Authority назначает группе epoch и lease, которые учитываются в маршрутизации каждого tenant. Перемещение одного tenant выполняется отдельной плановой миграцией по [ADR-004](../Task1/ADR-004.md).

Резервная копия не заменяет реплику: ежедневно полная резервная копия, непрерывный архив WAL, неизменяемое хранение 35 дней как проектная политика и регулярная проверка восстановления. Удаления и запреты обработки повторно применяются после восстановления прежде, чем открыть доступ.

## Альтернативы

**Синхронный WAL через WAN.** Он уменьшил бы окно потери при отказе региона, но каждый commit зависел бы от межрегиональной связи и её задержки. Выбраны синхронная реплика внутри региона и асинхронный DR с измеряемым lag; потенциальная потеря до RPO прямо учитывается при сверке операций.

**Active-active SQL, например перенос транзакционных доменов на CockroachDB.** Это потребовало бы смены СУБД, модели размещения quorum и проверки всех конфликтных инвариантов резервирования/денег. На этом этапе сохраняется PostgreSQL и один назначенный регион записи для группы данных; два независимых primary без консенсуса не допускаются.

**Только резервные копии или зеркалирование всех Kafka-топиков в обе стороны.** Восстановление из резервной копии не укладывается в региональный RTO 120 с. Безусловное двустороннее зеркалирование усложняет происхождение, дедупликацию и контроль разрешённых данных; выбраны тёплый DR и MM2 по allowlist без обратной репликации тех же origin topics.

## Компромиссы

Асинхронный DR допускает небольшую потерю подтверждённых локальных данных. Денежные операции после отказа требуют дополнительного состояния RECONCILING; новые поездки можно обслуживать раньше полного восстановления исторических витрин.
